# Persistencia de barriletes: propuesta para revisión

La comparación de la implementación anterior ponía la representación completa de `dailyBarriletes` en un filtro `value=eq.…`. El JSON y su codificación crecen con cada fecha: un fixture de 3.653 días excede los 100.000 caracteres codificados, antes de agregar el resto de la URL. Un navegador, proxy o API puede rechazar la solicitud antes de que PostgreSQL evalúe la condición.

El cliente ahora envía por POST a `save_barrilete_day` solo el usuario, una fecha y dos cantidades. La función propuesta mantiene la clave existente: valida y combina un día con el mapa actual dentro de la misma transacción. Toma un bloqueo de transacción por usuario incluso si todavía no hay fila y bloquea la fila encontrada antes de leer su valor. En READ COMMITTED, el siguiente escritor que use la función lee la versión confirmada. Las ediciones de fechas distintas se conservan; para la misma fecha prevalece el último guardado aceptado. El servidor aún lee y serializa el mapa completo, pero ni la URL ni el cuerpo del guardado crecen con el historial. Los duplicados, el JSON inválido y la falta de claves históricas se rechazan.

El cliente solo confirma el guardado si recibe la fecha y ambas cantidades esperadas. Si la función no existe, falla o devuelve una confirmación incorrecta, la edición queda pendiente para reintento. No hay escritura directa alternativa. El formulario, la alineación y el resumen semanal no cambian.

## Requisitos para una aplicación futura

1. Completar la revisión y recuperación del PR #8. Obtener autorización separada para instalar la función; no aplicar la restricción UNIQUE del #8 como parte de este cambio.
2. En un entorno desechable, confirmar el esquema de `public.cronograma`: tipos compatibles, `value` de texto, ID con default y permisos del rol real. La función es SECURITY INVOKER: no elude RLS ni amplía los permisos de tabla. Verificar que RLS limite el alcance del rol y que las siete claves y cualquier fila de barriletes existente sean visibles y coherentes. No conceder acceso si estas condiciones no se cumplen.
3. Con autorización, probar el archivo de [creación manual](sql-manual/save_barrilete_day.sql) y el [guion de prueba](sql-manual/test_save_barrilete_day.sql) en esa base. Confirmar POST y respuesta con el rol del cliente y probar dos conexiones en READ COMMITTED: mantener abierta la primera transacción tras crear la fila; desde otra conexión guardar otro día y comprobar que espera; confirmar la primera y verificar que queda una fila con ambos días. Repetir con una fila existente y comprobar que un duplicado visible o datos corruptos se rechazan sin modificar nada. Probar también que una operación sin permiso no crea filas ni devuelve confirmación.
4. Los bloqueos coordinan clientes que usan la función. Antes de habilitarla, cerrar versiones anteriores que escriban directamente la clave; sin una restricción única, un escritor externo que ignore el bloqueo podría crear duplicados. Revisar previamente las filas existentes. Si se necesita una garantía frente a todos los escritores, la restricción requiere su propia revisión y autorización.
5. Solo después de autorizar y verificar la función en el proyecto previsto, considerar desplegar el #9. No hay migraciones automáticas. Sin la función instalada, el #9 no debe promoverse a producción; los guardados fallarán de forma segura. Si hubiera que retirar la función, retirar primero la versión cliente que la llama.

La suite Node simula la RPC y comprueba la solicitud de tamaño constante, conservación de un historial de diez años, ediciones rápidas y concurrentes, reintento y ausencia de una ruta alternativa de escritura. Los archivos SQL quedan preparados: no se ejecutaron.
