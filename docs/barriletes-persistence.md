# Barriletes: autenticación y activación

El cronograma sigue usando su cliente y sus siete claves históricas existentes. La vista semanal comprueba de forma independiente una sesión de Supabase Auth para barriletes. El acceso no impide trabajar con actividades, metas, estrellas ni misiones. No se cambia el esquema, los permisos ni la autenticación de `public.cronograma` y no se realiza la recuperación histórica desde esta función.

## Uso diario

La primera vez, solo el pie semanal ofrece «Identificarme para barriletes». Se usa correo con enlace de acceso (PKCE): hay que solicitarlo y abrirlo en el mismo navegador y perfil. El enlace vuelve a la vista semanal. El cliente dedicado guarda la sesión en una clave propia del navegador y la renueva en segundo plano. Volver a abrir o recargar en ese navegador no pide otro correo si la sesión sigue vigente. Un error temporal admite reintento; una sesión revocada, un navegador nuevo o el borrado del almacenamiento pueden requerir un nuevo enlace. «Cerrar sesión de barriletes» aplica únicamente a esta sesión, sin tocar el cronograma.

## Tabla y autorización

[DDL manual](sql-manual/barriletes_daily.sql): `public.barriletes_daily(owner_uid uuid, day date, long_count bigint, short_count bigint)`, con clave primaria `(owner_uid, day)` y cantidades enteras entre 0 y el máximo entero seguro de JavaScript. `owner_uid` se genera con `auth.uid()`; la RPC de escritura no recibe propietario, y el rol del cliente no tiene permiso para insertar o actualizar esa columna. Los RPC con `SECURITY INVOKER` y las políticas RLS exigen la sesión del propietario y una entrada en `barriletes_private.allowed_users`. Esa lista queda fuera de esquemas expuestos y el cliente no puede escribirla. No se otorga acceso ni EXECUTE a `anon`, ni borrado a clientes. La única clave que se envía desde el navegador es publicable.

Cada guardado ejecuta un UPSERT atómico por fecha y confirma fecha y cantidades. Las ediciones concurrentes de fechas distintas no se pisan; para una misma fecha gana el último UPSERT aceptado, con ambos valores juntos. Solo se leen los siete días visibles. Los cambios pendientes se mantienen en memoria para reintentar; si la sesión termina se ocultan y solo se pueden recuperar en esa misma pestaña con la misma cuenta. Cambiar de cuenta descarta esos pendientes. El mapa anterior `dailyBarriletes` no se importa ni se borra. Si hubiera datos preexistentes, decidir su importación por separado.

## Configuración y pruebas en Supabase independiente

1. Confirmar que el proyecto y la clave publicable sean de un sandbox independiente. No enlazar el CLI ni aplicar SQL al proyecto de producción. Aplicar manualmente el DDL al sandbox. Mantener únicamente `public` entre los esquemas que se necesitan exponer; no exponer `barriletes_private`. Si la RPC anterior se instaló alguna vez en ese sandbox, revocar sus permisos o retirarla antes de validar la arquitectura nueva.
2. En Auth, habilitar Email y desactivar **Allow new users to sign up** y el inicio anónimo. El cliente también envía `shouldCreateUser:false`. En Usuarios de Auth, provisionar administrativamente la cuenta autorizada (para pruebas, solo cuentas ficticias). Con una cuenta administrativa y tras verificar el UUID desde Auth, insertar **únicamente** ese UUID en `barriletes_private.allowed_users`. La cuenta ficticia de control no debe estar en esa lista.
3. Configurar el **Site URL** exacto y permitir el callback explícito del sandbox, por ejemplo `http://127.0.0.1:8767/?barriletes=acceso`. No usar comodines de producción. Para activar más adelante, añadir el callback HTTPS con ese mismo parámetro en la URL aprobada de producción. Confirmar que el correo usa el enlace de confirmación estándar de Supabase, que el remitente está configurado y que el buzón de pruebas está disponible. No usar direcciones o contraseñas reales para pruebas. Ver [correo sin contraseña](https://supabase.com/docs/guides/auth/auth-email-passwordless), [redirecciones](https://supabase.com/docs/guides/auth/redirect-urls) y [configuración de Auth](https://supabase.com/docs/guides/auth/general-configuration).
4. Preparar siete filas **ficticias** para la ruta heredada en el sandbox, con el identificador que espera la app y un objetivo numérico de la semana actual, sin importar respaldos. Para revisar la UI, servir por HTTP una **copia temporal fuera del repositorio** de `index.html` y `app.js`, sustituyendo en esa copia exclusivamente la URL y clave publicable por las del sandbox. Verificar el destino antes de abrir el navegador. El despliegue real no es necesario.
5. Probar el flujo navegador: abrir sin sesión y verificar que el cronograma funciona; solicitar el enlace con el correo ficticio, abrirlo en el mismo navegador, guardar una fecha, cambiar de semana, recargar y reabrir el navegador. Verificar que no aparece el login al reabrir y que el token se renueva. Cerrar sesión y verificar que solo se ocultan los barriletes. Probar otro perfil con la cuenta no autorizada, una sesión revocada (revocar solo una cuenta ficticia), y después volver a identificar la cuenta habilitada. Confirmar que la cuenta anónima o sin permiso no puede acceder por PostgREST.
6. Para comprobar Auth y PostgREST con tokens reales, ejecutar `node tests/integration/barriletes-supabase.mjs` con estas variables, mediante un entorno temporal no versionado: `BARRILETES_TEST_URL`, `BARRILETES_CONFIRM_ISOLATED` (mismo origen exacto), `BARRILETES_TEST_PUBLISHABLE_KEY`, `BARRILETES_TEST_OWNER_EMAIL`, `BARRILETES_TEST_OWNER_PASSWORD`, `BARRILETES_TEST_OTHER_EMAIL`, `BARRILETES_TEST_OTHER_PASSWORD`. Las contraseñas son solo para este guion automatizado de cuentas ficticias, no para el flujo de la app. El script rechaza la configuración de producción de este repositorio, verifica dos sesiones concurrentes, renovación, cierre local, denegaciones, suplantación de propietario y compara las siete filas antes y después. Genera registros de barriletes ficticios en el sandbox. No imprime contraseñas ni tokens.
7. El [guion SQL local](sql-manual/test_barriletes_daily.sql) requiere las dos identidades sintéticas especificadas, se ejecuta como administrador sobre un PostgreSQL desechable y revierte sus datos al terminar. Complementa la prueba de API, no sustituye la validación de GoTrue, PKCE, correo y redirecciones reales.

## Requisitos pendientes para producción

- Completar por separado la revisión y recuperación del PR #8 antes de activar el #9. La seguridad del cronograma histórico requiere su propia revisión y plan.
- Pasar el protocolo en un sandbox conectado con credenciales de prueba. Las pruebas locales no validan ajustes del proyecto Supabase, correo real de acceso ni URLs de redirección.
- Con autorización posterior: configurar Auth y correo, confirmar que deshabilitar altas públicas no afecte otros consumidores del proyecto, habilitar la cuenta del propietario, aplicar el DDL manual y validar sus permisos. Si hubiera registros del contador anterior o si existe el RPC anterior, revisarlos por separado antes de cualquier traslado o revocación. No se incluye migración automática ni activación de producción en este PR.
